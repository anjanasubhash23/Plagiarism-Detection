# Design decisions

Each entry says what was chosen, why, and what it costs. Entries are added phase by phase.

## Phase 0: Audit and restructure

### D1. Rebuild, don't patch
The old scorer's core bug (TF-IDF fitted separately per text, then unaligned weight lists
compared by cosine) makes its scores meaningless, and the pipeline was tuned to one demo
pair. See `legacy/README.md`. Only the corpus is reused.

### D2. `legacy/` mirrors the original paths
Old code, templates, static files, POS data, stopwords, lexicon files and `ACCU_PER.docx`
were moved with `git mv`, so history follows them. Every file kept its relative path:
`legacy/X` was at `X`. That makes "where did this come from?" trivial to answer. Before and
after SHA-256 hashes confirmed that every moved file is byte-identical; only the
committed `__pycache__/*.pyc` files were deleted. The tag `v0-original` marks the
pre-rebuild commit.

### D3. The corpus has two layers: `data/raw` (originals) and `data/corpus` (derived)
- `data/raw/{topic}/*.docx` are the original files. They are never edited, and nothing writes
  to them. Topic folder names were lowercased; file names are unchanged.
- `data/corpus/{topic}/{doc_id}.txt` are generated by `scripts/build_corpus.py`. The script is
  deterministic (two runs produce byte-identical output), so the derived text is always
  reproducible from the originals.

### D4. doc_id = `{topic}-{NN}` from the number in the original file name
The original names are inconsistent (`Doc1`, `doc7`, `doc_1`, `DOC1`). The number in each
name is unique within its topic, so `ramayan-07` is stable and readable. `raw_path` in the
manifest links every id back to its original file.

### D5. Extraction rules
- **Reading the .docx:** standard library only (`zipfile` + `xml.etree`). A .docx is a zip
  of XML, and we only need paragraph text, so `python-docx` would be an unused dependency.
- **Normalisation: Unicode NFC only.** This is the canonical encoding and changes no visible
  character. Note that NFC deliberately decomposes precomposed nukta letters (U+0958–U+095F,
  e.g. `ज़`) into base + nukta. Any further normalisation (nukta, chandrabindu, etc.) is a
  detection-time choice for a later phase, not something baked into the corpus.
- **Line structure:** one paragraph per line, with leading and trailing whitespace stripped.
  Inner text is exactly as written.

### D6. Duplicates are recorded, not extracted
`Copy of doc_7.docx` is an exact copy of `doc_7.docx`, and the build script asserts this.
It stays in `data/raw`, gets a manifest row (`mahabharat-07-copy`,
`duplicate_of: mahabharat-07`, `path: null`), and gets no `.txt`. So it can never act as a
second "source" for the same text.

### D7. Five Paryatan docs: only the article is extracted
`DOC3`, `DOC4`, `DOC5`, `DOC6` and `DOC10` contain the article in paragraph 1, followed by the
prototype's pasted-in working notes: lemma lists, POS-tagged text such as `राम_NNP` and
synonym lists. Treating those as source text would put fake "sentences" into the index.
The files are declared explicitly in `ANNOTATED`; there's no heuristic. The script asserts
that paragraph 1 has no POS tags and that the rest does, so it fails loudly if the data ever
changes. Each affected row records this in `notes`. The originals in `data/raw` still
contain everything.

### D8. Sentence splitting reports problems instead of hiding them
Sentences are split on `।`, `?`, `!` and newlines, as specified. Six Mahabharat documents
(08–13) have no sentence-ending punctuation at all. Their dandas seem to have been
stripped, sometimes leaving a double space. They therefore count as one long "sentence"
each, and the manifest says so. We don't guess boundaries at extraction time, because
inventing sentence boundaries would quietly change the "ground truth" that source tracing
is evaluated against. How to segment these documents is a Phase 1 decision.

### D9. Word count
A word is a run of Devanagari letters and signs (excluding the dandas), Latin letters or
digits. Python's `\w` can't be used: it doesn't treat vowel signs (matras) as word
characters, so `\w+` splits `किताबें` into `क`, `त`, `ब`.

### D10. Lexicons are merged but quarantined
- **Merged:** the four lemma files and four synonym files become `data/resources/lemmas.tsv`
  and `synonyms.tsv`.
- **Normalised:** text is NFC with whitespace collapsed; `word : same word` lines are dropped
  as no-ops; duplicates are merged.
- **Traceable:** each row lists every `file:line` it came from.
- **Status column:**
  - `review`: flagged.
  - `pending`: not flagged, but unapproved.
  - `approved` / `rejected`: set by a human; the script preserves these on re-runs.
- **Quarantined:** no code may use these files until a human approves rows. Many entries are
  wrong (e.g. `पहनना → आसंजन`, "wear → adhesion"), and a bad synonym in a detector produces
  false accusations.

Flags come from two places:
- **Mechanical rules** in `build_resources.py`:
  - phrase vs single word;
  - for lemmas, a word with several different lemmas, or a lemma that doesn't start like
    the word.

  These are cheap and transparent but blunt. For example, `गया → जाना` is flagged even though
  it's correct, because Hindi's past tense of जाना is irregular.
- **A reading of every synonym pair** (all 630), recorded with a reason in
  `data/resources/review_notes.tsv`. The reason categories are: different meaning, different
  part of speech, related-but-not-synonym (broader or narrower term), inflection/spelling
  variant, garbled word, proper noun replaced by a description, and ambiguous source word.
  Keeping these in a file, rather than editing the TSV, makes the flags reproducible and
  shows exactly who decided what. This is a first pass to speed up human review, not a
  substitute for it.

Finding: most lemma conflicts come from two conventions mixed across files. Verbs are
lemmatised to the stem in some files (`आया → आ`) and to the infinitive in others
(`आया → आना`). A single convention has to be chosen before the lemma list can be used.

### D11. Near-duplicate scan: character 5-gram Jaccard > 0.25
Character n-grams need no tokeniser and tolerate small spelling differences, which is
enough for a corpus health check. Limitation, observed on this corpus: Jaccard divides by
the union of both documents, so a shared passage inside two otherwise different
documents is diluted. `ramayan-05` and `ramayan-08` share a 65-word passage but score
0.233, just under the threshold. The report prints the top pairs below the threshold so
this stays visible. A containment-style measure (overlap ÷ smaller document) would catch
it; that belongs to the detection phases.

### D12. Tooling
- **Packaging:** uv + `pyproject.toml`, with a src layout (`src/srot/`), so tests import the
  installed package rather than whatever is in the working directory.
- **Python:** `requires-python >= 3.11`, with 3.12 pinned in `.python-version` for development.
- **Linting:** ruff for lint and format (rules E, F, I, UP, B, SIM).
- **Dependencies:** none at runtime; `pytest` and `ruff` are the only dev dependencies. Each
  later dependency must be used by code in the same phase.
- **Secrets:** `.env` is git-ignored now, ahead of the LLM client module.
